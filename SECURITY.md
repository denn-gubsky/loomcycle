# Security policy

## Supported versions

Security fixes land on `main` and ship in the next release of the **latest minor line** only. Older lines get no backports: upgrade to the latest release.

| Version | Supported |
| ------- | --------- |
| 1.146.x (latest minor) | Yes |
| Anything older | No |

The table moves with each minor release; the [releases page](https://github.com/denn-gubsky/loomcycle/releases) is authoritative. The same rule covers the adapters and packages published from this repo (`@loomcycle/client`, the `loomcycle` Python package, the `@loomcycle/*` npm packages, the Docker images): the latest published version is the supported one.

## Reporting a vulnerability

**Do not open a public issue, discussion or pull request for a vulnerability.**

Report it privately through GitHub Security Advisories: the **Report a vulnerability** button on the repository's Security tab, or directly at

<https://github.com/denn-gubsky/loomcycle/security/advisories/new>

The report and the discussion stay private between you and the maintainers until a fix is published.

If the **Report a vulnerability** button is not available, contact the maintainer privately through the email address on their GitHub profile. Never through a public issue.

Please include:

- the affected version (`loomcycle --version`) or commit, and how it was installed (Homebrew, Docker, binary, source);
- the relevant configuration: auth mode (open, shared token, per-principal tokens), enabled tools, volumes, storage backend. Redact every secret;
- the surface involved: HTTP/SSE, gRPC, MCP, Web UI, an adapter, a tool, a provider driver;
- steps to reproduce, ideally a minimal config plus the requests or prompt that trigger it;
- the impact as you see it: what an attacker controls, and what they gain.

## What to expect

These are targets, not guarantees:

- **Acknowledgement** within 3 business days.
- **Triage** (confirmed or not, severity, affected versions) within 10 business days.
- **Fix:** critical and high severity in the next patch release, as soon as a fix is verified; medium within about 30 days; low in a regular release.

We keep you informed while we work on it, credit you in the advisory unless you ask us not to, and publish a GitHub Security Advisory (with a CVE where one applies) when the fixed release is out.

## Coordinated disclosure

Please give us the time to ship a fix before you disclose publicly. We will agree a disclosure date with you; the default is the release of the fix, and at most 90 days after the report. If a vulnerability is already public or being exploited, tell us and we will move faster.

## Scope and threat model

In scope: the `loomcycle` binary and its Web UI (embedded or loaded at runtime), the wire surfaces (HTTP/SSE, gRPC, the MCP server), the adapters and packages in this repo (the chat bridges included), the deployment files under `deploy/` and `cloud-deployment/`, and the Docker images and release artifacts built from it.

This model describes v1.142.0 (2026-11-06). That release shipped most of what the 2026-11-04 re-assessment asked for (RFC FZ): the store-backed audit trail, each SQLite scope's documents in a file of their own, bounded table extraction and the extraction limit, fact provenance for runs and `sync`, the required `issued_token` ceiling on an external gate, the response headers, `cidr_only`, the redactor bound, the helper wrapper, the SQL result byte cap, and signed releases with SBOMs and provenance. v1.141.0 brought SQLite defensive mode and the Memory SQL name guard, and v1.140.0 the member-plane confinement (RFC FY). The bridge changes ship in the bridge packages' own 0.4.0 releases.

### Who is trusted

- **The operator** (the config files, the environment, the host) is trusted completely. The operator's static lists (allowed hosts, tools, scopes, gates) are the floor no caller and no model can widen.
- **A caller** is whoever holds a bearer or a session. It is trusted with exactly the `(tenant, subject, scopes)` its credential resolves to; the wire `tenant_id` / `user_id` never decide. The shared `LOOMCYCLE_AUTH_TOKEN`, an admin-scoped minted token and open mode are the operator.
- **A model is never trusted.** Nothing a model writes becomes an authorization decision, an allowlist entry or a capability; a run holds only what its agent's grants and its caller's rules allow, whatever token started it.
- **Content is never trusted**: files, web pages, tool results, MCP responses, peer documents and chat messages are data that may carry prompt injection.

### Documented properties of a posture

Some behaviour is a documented property of the posture an operator chose, not a vulnerability. Read these before reporting:

- **The `Bash` tool is not a sandbox.** When enabled it runs real host processes that can reach absolute paths and the network. Run loomcycle in a container or VM if `Bash` is exposed to untrusted prompts. See [`docs/TOOLS.md`](docs/TOOLS.md#built-ins).
- **Open mode is for localhost only.** With no `LOOMCYCLE_AUTH_TOKEN` and no minted tokens, every request is allowed as an admin; the server refuses to start that way on a non-loopback listener unless `LOOMCYCLE_ALLOW_OPEN_MODE=1`. See [README: Tier 1](README.md#tier-1-zero-config-dev-open-mode-localhost) and [`docs/CONFIGURATION.md` §9b](docs/CONFIGURATION.md#9b-multi-tenant-authentication-rfc-l) for the authenticated modes.
- **Bashbox and gbash maturity.** `Bashbox` runs commands in gbash, an in-process sandbox with no OS process and no network; gbash is alpha and pinned. It is a strong layer for untrusted prompts; for mutually hostile tenants on one process, also run loomcycle in a container. Commands an operator allowlists for host fallback run on the real host. See [`docs/TOOLS.md`](docs/TOOLS.md#built-ins) and the `bashbox` help topic.
- **A private host vouched for by name trusts its DNS.** An entry in `LOOMCYCLE_HTTP_PRIVATE_HOST_ALLOWLIST` that is a host name (suffix-matched) lets every outbound request loomcycle makes (the HTTP and WebFetch tools, MCP over HTTP, A2A, hook webhooks, remote memory and document peers, git sources) reach that name wherever it resolves: loopback, RFC 1918, CGNAT or ULA. Whoever controls the name's DNS, or can create a name under a suffix entry, can point it at another private service. A vouched name never reaches a link-local or cloud-metadata address; only a CIDR entry covering the address admits those. To trust no DNS, set `LOOMCYCLE_HTTP_PRIVATE_HOST_ALLOWLIST_MODE=cidr_only`: a name entry in this list or in `LOOMCYCLE_HOOKS_PRIVATE_HOST_ALLOWLIST` fails config load, a yaml-declared remote peer is not vouched for by its host name, and the operator's MCP servers dial through the guard (`LOOMCYCLE_MCP_ALLOW_PRIVATE_IPS=1` fails load). A hook webhook dials unguarded only when it is written inline in the operator's yaml; a stored HookDef is guarded whoever names it. See [`docs/TOOLS.md`](docs/TOOLS.md#built-ins) and [`docs/CONFIGURATION.md` §9c](docs/CONFIGURATION.md#9c-environment-files--secrets-vs-config-envlocal--envinsecure).
- **Operator-token hashes are peppered only with a secret.** A token row stores a hash, never the token. The pepper that stops a database writer from inserting a row for a token of their choosing is `LOOMCYCLE_OPERATOR_TOKEN_PEPPER`, or one derived from `LOOMCYCLE_SECRET_KEY`. With neither, rows are hashed with no pepper and the server only warns at boot. Set `LOOMCYCLE_SECRET_KEY` on any deployment with minted tokens. See [`docs/CONFIGURATION.md`, Token pepper](docs/CONFIGURATION.md#token-pepper).
- **Volumes are the filesystem boundary.** An agent reaches the disk only through the volumes bound to it; `Bash` and Bashbox host-fallback commands are not confined by them. See [`docs/CONFIGURATION.md` §9d](docs/CONFIGURATION.md#9d-filesystem-volumes--per-agent-rorw-scopes-rfc-ah) and the `volumes` help topic.
- **A repository the `Git` tool wrote is not safe for a host `git`.** The `Git` tool runs no `git` program, so nothing a repository's configuration names (hooks, `core.fsmonitor`, filter drivers) executes inside loomcycle. A host `git` that later runs on a volume an agent could write will execute whatever hooks or configuration the agent planted there. See [`docs/TOOLS.md`](docs/TOOLS.md#the-git-tool).
- **The output redactor is process-wide and bounded.** Values a run's tools resolve or receive (`$cred:` values, minted tokens, provider and peer keys, the credential parts of a fetched URL) are masked in every tenant's output, not only the registering tenant's; short URL parts are not registered for that reason. Values a live run registered are pinned and never evicted; unpinned credentials share one 4,096-value LRU, and observed URL parts a smaller per-tenant bucket, so a value can stop being masked once no live run holds it and newer ones have displaced it. What was written while it was registered stays masked in the store.
- **The code sandbox sidecar** has its own isolation posture: [`docs/SANDBOX.md`](docs/SANDBOX.md#isolation-posture).

### Sign-in gates and sessions

- **What a gate decides.** A gate (OIDC, OAuth, password with TOTP, passkey, external, header, AWS IAM, device, SCIM) establishes only *who* a person is: the subject `<gate>:<claim>`. The tenant and the reach come from the gate's `identity_map` in operator config, never from the assertion. A pending user gets `403 awaiting_approval` and no token; a token issued through a gate stops working once the user is not `active` or the gate leaves the config. Gates exist only in config: no API call adds one.
- **What a bridge may assert.** An external gate (a chat bridge) signs a short-lived JWT (Ed25519, P-256, or HS256 with a secret of at least 32 bytes; `aud` = `LOOMCYCLE_PUBLIC_URL`; at most 5 minutes; single-use `jti`). It can only assert people inside its own `identity_map`; only a `trusted: true` gate may assert an access mode or groups, and only its own `<gate>:` groups; its `amr` is forced to `ext`, so it never stands in for a second factor. A stolen bridge credential cannot act as an operator.
- **The `issued_token` ceiling is required.** An external gate must declare the most a token it gets for a person may carry (agents, speech surfaces, per-run overrides, TTL, rate, active tokens); the assertion can only narrow it. `issued_token: unrestricted` (or `{unrestricted: true, ttl, rate, max_active}`) must be written out to issue wide tokens. A gate without the key fails config load. The ceiling bounds the tokens the gate issues, not a browser sign-in: on a gate with `callback_url`, whoever holds the gate's key can sign any of its users in to the Web UI with that user's whole member reach (and from there start an app sign-in or a device login). Guard such a key as you would the users' own credentials.
- **`auth:manage` reaches across tenants.** A token with `auth:manage` (minted alone, refused on gRPC) reaches `/v1/_authgate/*` and the user records of **every** tenant, and nothing else. It is meant for a sign-up website's backend; refusals are audited (`auth_manage_refused`). With `manager_may_recover_owners: true` it can take over any owner's account; leave that off unless the website is as trusted as the operator.
- **No consent screen for runtime clients.** `auth.clients` and ClientDef make loomcycle an OAuth authorization server for apps (PKCE S256 only, exact redirect match, single-use 60 s codes, refresh rotation with reuse detection). It is not an OpenID Connect provider and shows no consent screen: only clients an admin or tenant operator registered exist, and the registered redirect URI decides where codes go. Signing out of the Web UI does not end app sign-ins; a person lists and ends their own with `GET`/`DELETE /v1/_me/app-sign-ins`, a tenant operator a user's with `/v1/_users/{subject}/app-sign-ins`.
- **`gate_only` and machine credentials.** Under `auth.mode: strict`, `auth.strict.user_tokens: gate_only` refuses a hand-minted personal token on every transport. Machine credentials are unaffected by design: operator and tenant tokens, service tokens (whose subject is no user), `auth:manage`, `scim:provision`, declared principals and `LOOMCYCLE_AUTH_TOKEN`. A user created later for a service token's subject makes that token personal.
- **A credential change ends every sign-in.** A password reset ends all of the person's sign-ins — app sign-ins (refresh tokens), delegated and device-login tokens, and every Web UI session — and a self-service password change ends all but the browser that made it. A disable, an erasure, a user delete and an operator's credential removal end the same set, through one routine; removing a passkey or the authenticator app ends the person's app sign-ins and delegated tokens. A sign-in in flight when the change lands (a code exchange, a device-code redemption) re-checks its approving session after writing and ends itself. **A reset removes no passkey**: one added by someone who knew the old password still signs in afterwards, so the reset page lists the account's passkeys for the person to check and remove. Operator and tenant-operator tokens (`substrate:admin`, `substrate:tenant`) and config-declared principals are roles, not the person's sign-ins: a per-subject teardown leaves them — retire them with `operatortokendef` or the config. An app's own token cannot list or end app sign-ins.
- **Account lockout is a denial of service.** A password-gate account locks for `lockout_minutes` (default 15) after `max_failures` (default 10) wrong passwords in a row, counted in the store across replicas. Anyone who knows a login can keep it locked by sending wrong passwords; the per-address and per-address-and-login throttles slow one client but not many addresses. The lock applies to the password only: a passkey, an identity gate (OIDC, OAuth) or a reset link still signs the person in, and setting a new password (reset or invite) clears the lock. Operators who expect targeted lockouts can give people a second way in (passkeys), raise `max_failures` or shorten `lockout_minutes`; `auth_login_locked` audit events show who is being locked. Progressive per-account delays instead of a hard lock are not implemented.
- **Removing a passkey ends a session bound to it on that session's next request**, not at the moment of removal: the session row stays until it is used, then fails its credential check and is revoked. The same lazy check covers any session whose credential (password, linked identity, token) changed.
- **A JWKS fetch holds the key-set lock.** An OIDC or external gate that verifies against a remote JWKS fetches it under one lock, on purpose, so concurrent sign-ins that miss a key wait for one fetch instead of each making their own. A slow key endpoint therefore delays every sign-in through that gate for up to the fetch timeout (10 s by default); a failed fetch keeps the keys already held, and refreshes are rate-limited.
- **Sessions.** Web UI sessions are server-side (the store holds a hash of the id); the cookie is `__Host-lc_session` (`Secure; HttpOnly; SameSite=Strict`) over HTTPS, decided from `LOOMCYCLE_PUBLIC_URL` (no forwarded header is trusted); state changes need `X-Loomcycle-UI: 1` from the same origin; idle 8 h, absolute 168 h, re-authentication window 15 min by default.
- **Not defended:** a provider that reassigns the subject claim (`identity_map.subject_claim_immutable: true` is the operator's word that it does not; any claim but `sub` needs it); a header gate behind a proxy that does not strip the header (`trusted_proxy_cidrs` is required, `0.0.0.0/0` refused); any peer in `auth.trusted_proxies` or `auth.grpc_trusted_proxies` naming its own client address, which throttles, audit and `source_cidr` rules read (a catch-all is refused at load, a range wider than /16 or /48 warns); plain-HTTP sessions under token mode or `LOOMCYCLE_UI_INSECURE_COOKIES=1`.
- **Knobs:** `LOOMCYCLE_AUTH_MODE` (a reload cannot lower it), `LOOMCYCLE_PUBLIC_URL`, `LOOMCYCLE_UI_INSECURE_COOKIES`, `LOOMCYCLE_UI_LOGIN_ORIGINS`, `LOOMCYCLE_USER_TOKEN_MAX_TTL_SECONDS`, `LOOMCYCLE_AUTH_CACHE_TTL_SECONDS`. See [Web UI sign-in](docs/CONFIGURATION.md#web-ui-sign-in--sessions-authmode-and-gates-rfc-fa), [the external gate](docs/CONFIGURATION.md#external-gate--kind-external-rfc-fa-p4), [header and AWS IAM gates](docs/CONFIGURATION.md#header-and-aws-iam-gates--kind-header-kind-awsiam-rfc-fa-p3), [strict mode](docs/CONFIGURATION.md#strict-mode-personal-tokens-only-from-a-gate--authstrictuser_tokens-rfc-fa-4) and [app sign-in](docs/CONFIGURATION.md#app-sign-in--authclients-and-clientdef-rfc-fl).

### Access control

Access-control rule lists, nested groups and bindings sit on top of the per-route and per-RPC scope gates. `LOOMCYCLE_ACL` picks how much they decide:

| `LOOMCYCLE_ACL` | Who decides | An explicit ACL deny | No rule matches |
|---|---|---|---|
| `compat` (default) | the scope gates | refused | the scope gate's answer |
| `shadow` | the scope gates | **logged only** (`acl_shadow_diverged`), not enforced | the scope gate's answer |
| `enforce` | the rules (the built-in baselines included) | refused, `403 acl_denied` | refused; an unreadable rule set is `503 acl_unavailable` |

- **`compat` keeps the scope gates authoritative**: a rule can only take away. `shadow` is for measuring a rollout and enforces less than `compat`; do not run it where an explicit deny must hold.
- **Every stored rule is enforced or refused.** A rule naming a (verb, type), condition or transport no surface evaluates is refused at write (`400 rule_not_enforceable`), as is a selector naming some instances of a verb asked only of every instance (`deny read run:tenant`, `allow cancel run:own`), which would refuse nothing or admit every instance; the table of what is asked where is `internal/authz/enforced.go`, held to the code by census tests, which also hold every MCP meta-tool op and every gRPC RPC to the question its HTTP twin route asks. A tenant list may not take a config or shared list's name (`409 acl_name_reserved`).
- **Caller tiers.** Every transport stamps one of four tiers on a call: the **operator plane** (admin, the legacy token, open mode, or `substrate:tenant` in its own tenant, calling from outside a run), a **member**, an **isolated** member, or a **run**. Operator authority (the tenant ontology, the review policy, reserved names, operator-grade agent fields) is never exercised from inside a run, whatever token started it. An unstamped call is a run.
- **Not defended:** an agent handed an admin bearer for `/v1/_mcp` gets an operator session; do not give agents admin bearers. A run keeps the rules it started with unless `LOOMCYCLE_ACL_LIVE=1`.
- **Knobs:** `LOOMCYCLE_ACL`, `LOOMCYCLE_ACL_CACHE_TTL_SECONDS`, `LOOMCYCLE_ACL_LIVE`. See [the caller tiers](docs/CONFIGURATION.md#who-acts-as-the-operator--the-four-caller-tiers), [config-declared access control](docs/CONFIGURATION.md#config-declared-access-control-rfc-ey) and [managing lists and bindings](docs/CONFIGURATION.md#managing-groups-acl-lists-and-bindings).

### Tenant members

- **Trust model.** A tenant is one trust domain. A non-isolated member shares the tenant scope (its memory, documents and Path tree) with every other member and agent of the tenant, and its agents may write there within their grants. Give a person who must not see shared tenant data `access_mode: isolated`, which confines them to their own user scope.
- **Conversations are not shared.** Every member, isolated or not, reads, continues and acts on only the runs and sessions it started, and uses only its own user-scoped channels, on HTTP, gRPC, MCP and A2A; another user's run and a tenant-level run (an operator's, a schedule's, a webhook's) answer as a missing one does. The schedules and webhooks a member writes run only as itself. A tenant operator reads every run of its tenant, an admin every run. See [whose conversations a caller reads](docs/CONFIGURATION.md#who-acts-as-the-operator--the-four-caller-tiers).
- **What `?scope_id=` a member may pass** on the off-run memory, Document, Path, feed and asset routes: itself; a subject its rules let it `browse` (`browse memory:user` / `browse document:user` with `owner_is_self: false`), read-only; an agent it may run, read-only. Anything else is an opaque `404`, the same for every subject. A member's `?tenant=` changes nothing.
- **What a member cannot do:** user and gate management, erasure, the ontology and review policy, budgets, access-control management, client registration, retention overrides, the Crypto routes and the audit export. Agents a member authors are held to a ceiling: operator-grade fields (`statement_methods`, `git_remote`, `*_def_scopes`, tenant and run crypto) must be unset.
- See [what `?scope_id=` a member may pass](docs/CONFIGURATION.md#who-acts-as-the-operator--the-four-caller-tiers) and [the external API](docs/EXTERNAL_API.md#authentication).

### Subject erasure

- **What it removes** (dry run by default; a live run needs `confirm` equal to the subject, a tenant operator or admin (members are refused), and a working audit sink, else `503 audit_unavailable`): the person's chats, user-scope memory rows, Path names and SQL Memory scopes, credentials, budgets and usage carry-over, interrupts, group memberships and bindings, member tokens, every sign-in family (identities, password, TOTP, passkeys, sessions, app sign-ins, SCIM links), and subject bindings. The user row becomes a tombstone that cannot sign in or be re-created.
- **What it cannot reach**, and reports as retained: the audit trail (the store-backed chain and the JSONL file; they age out only through `LOOMCYCLE_AUDIT_RETENTION_DAYS`), the usage ledger, tenant-scope residue it can trace only by provenance (facts written without provenance are not reachable at all), the identity provider's own account, privileged operator-token rows and config-declared principals or rules.
- **Not reached and not reported:** model providers' logs, database backups, runtime snapshots already taken (restoring an older one brings the data back), retention exports (`LOOMCYCLE_RETENTION_EXPORT_DIR`), log and trace pipelines, and JSONL audit files on other hosts. The erasure response is the only durable record of what was not reached; keep it.

### The audit trail

- **What it is.** Token, gate, user, approval, access-control, erasure, run-tree, statement-ruling, crypto, git and directory events go to a store-backed stream: one hash chain per tenant (plus an operator chain), appended by every replica through the store so replicas never fork a chain. Each row's hash covers the previous hash and the row's exact stored bytes; each row, the head and the retention anchor carry an HMAC under a key derived from `LOOMCYCLE_SECRET_KEY`. The `LOOMCYCLE_AUDIT_LOG_PATH` JSONL file is an optional per-replica, unsigned mirror; SQL Memory statement records go to the file only.
- **When it is on.** Without any setting whenever a sign-in gate, `auth.mode: strict`, a `LOOMCYCLE_ACL` other than `compat`, or more than one principal is configured (counting the legacy `LOOMCYCLE_AUTH_TOKEN`, each config principal whose token is set, and, at boot, each live operator token in the store; more than one tenant implies more than one principal). Then config load refuses a deployment without `LOOMCYCLE_SECRET_KEY` and the server refuses to start if it cannot open the stream, or with `LOOMCYCLE_AUDIT_STORE=0`. A config reload that would raise the requirement on a server that started without the stream is refused (restart instead). A single-operator deployment (one credential) keeps the file-or-nothing behaviour unless `LOOMCYCLE_AUDIT_STORE=1`. The posture is read at boot: a token minted afterwards on a single-operator deployment takes effect at the next start.
- **Defended:** a database writer without the key cannot edit, insert or reorder rows unnoticed: `loomcycle audit verify --tenant <t>` (or `--operator`, `--all`) walks each chain, and `GET /v1/_audit` (tenant operators get their own chain; the operator chain needs admin) exports it with a signed trailer, which `loomcycle audit verify --export <file>` checks offline (with `LOOMCYCLE_SECRET_KEY` set, the signatures too, and an empty or unsigned file is not OK; without it only that the file is consistent, which anyone can forge; a file that starts mid-chain needs `--allow-partial`). Each tenant chain's signed head is checkpointed into the operator chain every 100 rows, every 5 minutes while rows are uncovered, and at a clean shutdown, so rolling a tenant chain back to an earlier signed head (from a backup, a replica or an export) fails verification, and a retention prune refuses to fold such a rollback under a new anchor.
- **Recorded before the change.** Token mints, rotations and retirements, access-control list, binding, group and membership writes, and user create, update, disable, delete and SCIM create, deactivate and re-enable write their audit row before the change is made (marked `change_status: intent`; a change that then fails gets a `failed` row, or a `partial` row with `change_counts` when it stopped after applying some of it, as a snapshot restore can). When the row cannot be written, what happens depends on the change:
  - **Grants are refused:** a token mint or rotation (including the token a gate issues at sign-in), a user create, approval, re-enable or other update (a disable that also raises the access mode or renames counts as an update), a SCIM create, re-enable or attribute update, a snapshot restore, and every access-control write: `503 audit_unavailable` on HTTP and SCIM, a transient `audit_unavailable` error on the gRPC and MCP twins. Access-control writes all count as grants because each can remove a deny (a list rewritten or retired, a binding retired, a group deleted, a member removed).
  - **Reductions go ahead:** a token retirement, a user disable (that changes nothing else) or delete, a SCIM deactivation or delete. An operator must be able to revoke a compromised credential while the audit store is down. The record is retried after the change, the miss is logged at error and counted in `loomcycle_audit_unrecorded_total{action}`; alert on it being non-zero.
  - Erasure stays refused without a working audit sink (it is the one change nothing can undo). This applies whenever an audit sink is configured (the store stream or the JSONL file); a single-operator deployment with none records and refuses nothing. This refines decision D3 of the hardening RFC (fail closed) for access-reducing changes.
- **Best-effort, by design.** Sign-in events (logins, failed logins, sessions, OAuth codes and refreshes), and the changes made inside one — except the bearer token a device, external or AWS IAM gate issues, which is a grant: that sign-in fails with the audit store down — (a gate's group sync, an invite's group membership, token retirements while a disable, removal or erasure ends a user's access, the removal policy's own stages) log a failed append and go on: refusing them would lock people out, or keep a credential alive, whenever the audit store is unavailable. Observations (failed sign-ins, denials, lookups) are queued with a per-tenant share, and overflow is counted in a row, not silently lost.
- **Credential writes outside the recorded-ahead set.** A person's own sign-in credentials are written best-effort, after the fact: setting or changing a password (invite redemption, reset, self-service change), enrolling or removing TOTP, registering, renaming or removing a passkey, linking an identity at sign-in or through a link invite (`UserIdentityCreate`), an operator unlinking one (`UserIdentityDelete`), and a SCIM resource's own attributes (`SCIMUserUpdate`; the user change a SCIM update makes is recorded ahead). An operator renaming a login (`auth_login_renamed`) is recorded ahead as a grant.
- **Not defended:** deleting every chain at once, rolling the operator chain back together with a tenant chain, and removing the rows a tenant chain gained since its last checkpoint all verify cleanly; detecting them needs an outside witness (export the heads elsewhere). Whoever holds `LOOMCYCLE_SECRET_KEY` can rewrite history. Queued observations past the queue are dropped (and counted).
- **Knobs:** `LOOMCYCLE_AUDIT_STORE`, `LOOMCYCLE_AUDIT_RETENTION_DAYS`, `LOOMCYCLE_AUDIT_LOG_PATH`, `LOOMCYCLE_SECRET_KEY` / `LOOMCYCLE_SECRET_KEY_PREVIOUS`. See [`docs/CONFIGURATION.md`, Audit trail](docs/CONFIGURATION.md#audit-trail).

### Documents and the knowledge base

- **Untrusted files are parsed in process.** `File op=extract` reads DOCX, ODT, XLSX, PPTX, PDF, HTML, CSV/TSV, captions and images with pure-Go parsers inside the loomcycle process. Bounds: zip entries, expansion and per-entry ratio; XML with no DTD entities and capped elements and depth; per table 16 MiB, 200,000 cells and 200 columns; 32 KiB per cell; 32 MiB of tables per document; `max_rows` at most 10,000; XML attributes capped per element (1,024), per part (2,000,000) and in value bytes (64 MiB), counted before decoding; HTML pages at most 8 MiB and counted with the tokenizer before parsing (elements and text runs, attributes, and the formatting elements the parser would re-create); PDF pages capped on characters and decoded bytes. The `File` tool gives each extraction 60 s once it holds a slot; PDF, XML and HTML parsing stop at that deadline at their next read or check, and the slot is released. Measured at every cap at once, one file can take about 700 MiB (an Office XML part's tree plus the part, up to the 256 MiB archive budget) and an HTML page about 280 MiB. At most `LOOMCYCLE_EXTRACT_CONCURRENCY` extractions run at once (default: the processor count), so give the container at least 1 GiB plus about 750 MiB per concurrent extraction, or lower the concurrency. A panicking parser costs one failed tool call (`tool_panicked`, counted in `loomcycle_tool_panics_total`), not the process. Each document format's extractor is fuzzed.
- **Not defended:** extraction is not a separate process with a memory limit; the bounds are the defence, and a parser bug inside them shares the process. Run loomcycle in a container with a memory limit.
- **Prompt injection into tenant facts.** Imported text is tagged `untrusted`, fenced in excerpts and never served as a remembered fact. In the tenant scope, which every member reads, every relation a run chooses (`link_chunks`, a fact's relation, import and canvas edges, copied or moved relations) is filed as a **proposal** for review unless the agent holds `statement_methods: [link]`; it is recorded with the run as actor and method `agent`, never as a person's `manual`. `remember`, which files a sentence as something a person said, needs `statement_methods: [remember]` from inside a run. A `sync` pull writes only into its bound document and files the peer's links as proposals unless the operator declares the source `trust: asserted`. A machine ruler (a policy or a judge) rules only on proposals and never reverses an operator's rejection.
- **Not defended:** a person who accepts an injected proposal; an agent the operator granted `link`, `remember` or a `rule:` method; a source declared `trust: asserted`. Those are the operator's choices. See [`docs/DOCUMENTS.md`, What a statement is](docs/DOCUMENTS.md#what-a-statement-is) and [Sync](docs/DOCUMENTS.md#sync).
- **SQLite versus Postgres.** On Postgres each SQL Memory scope's Document plane is its own schema behind its own login role, which the agent's role cannot use: that is the isolation-grade tier. On SQLite each scope's documents live in their own file, `<scope>.doc.db`, beside the agent's `<scope>.db`; Memory SQL only ever opens the agent's file and can neither `ATTACH` nor `VACUUM INTO`, so the document tables are not there to name. Every scope connection, the document file's included, runs in defensive mode (no page writes, `writable_schema` ignored), and Memory SQL still refuses the document tables and the names that reach the file beneath them (`sqlite_dbpage`, `dbstat`, the schema tables, `sqlite_stat*`, every `pragma_*` function) in every quoting form, plus planted views and triggers. An agent's SQL result is capped at `LOOMCYCLE_SQLMEM_MAX_RESULT_BYTES` (default 8 MiB) and `LOOMCYCLE_SQLMEM_MAX_ROWS`; on SQLite its statements also run with the engine's value length limit at twice that cap, so a value such as `zeroblob(400000000)` is refused before it is built. On Postgres there is no engine value limit; the hard bound is the connection, which during an agent's statement refuses any message from the server over twice the cap (plus 1 MiB) from its length header, before reading it. Earlier checks give clearer errors: agent reads are wrapped so the server refuses an oversized row before sending it, `sql_exec` refuses statements that return rows, and a `repeat`/`lpad`/`rpad` length must be a constant. The server may still build an oversized value, within `statement_timeout`. Each scope role carries `temp_file_limit` 1GB when the admin is granted `SET` on it (a superuser setting the role cannot change) and `work_mem` 16MB, which is only a default the role can change in its session. For mutually distrusting tenants, use Postgres. See [`docs/SQL_MEMORY.md`](docs/SQL_MEMORY.md#the-document-tools-tables-are-off-limits).

### Transcription, speech and helper programs

- **Egress.** OCR sends PDF pages (a Claude model: the page range as a document; another vision model: one rendered image per call) to the configured vision provider; speech-to-text sends audio, in pieces under 25 MB, to the configured `openai-audio` endpoint (a self-hosted whisper server or OpenAI); text-to-speech sends the text to the speech engine; embedders receive the text they embed. Each is off until the operator configures it, and OCR also needs the agent's opt-in. Choose self-hosted engines to keep content on your network.
- **Helpers.** `pdftoppm` (OCR rasterising), `ffmpeg` (media conversion) and the speech encoder run with no shell, a scrubbed environment, a fenced working directory, their own process group, bounded output and a 5-minute default timeout, but **as the loomcycle user**: they parse hostile files natively and can read whatever the process can. `LOOMCYCLE_HELPER_WRAPPER` (for example a `bwrap` or `systemd-run` command line, split into argv with no shell) is prepended to every helper and is the confinement. `ffmpeg` always gets `-nostdin -protocol_whitelist file,pipe` before each input, so nested protocols cannot fetch; local files a demuxer opens are limited only by the wrapper. A descendant that calls `setsid` escapes the process-group kill.
- See [`docs/CONFIGURATION.md` §9h](docs/CONFIGURATION.md#9h-transcription--ocr-and-speech-to-text) and [`docs/TOOLS.md`](docs/TOOLS.md#files-tools-return--the-run-inbox-and-the-file-tool).

### The chat bridges

- **Trusted:** the platform's signature on inbound requests and the bridge's gate key. A bridge running as a gate signs people in through loomcycle and holds no operator token (it refuses a stray `LOOMCYCLE_TOKEN`).
- **Defended:** `BRIDGE_DEV=1`, which skips the platform's signature check, is refused together with `BRIDGE_GATE` and refused off loopback. `LOOMCYCLE_BASE_URL` must be https unless it is loopback or `BRIDGE_ALLOW_INSECURE_LOOMCYCLE=1`. A revoke loomcycle did not take is kept and retried (1 min to 1 h backoff; persisted with `BRIDGE_STORE=file:`). A platform that can list its members (Slack) is reconciled every `BRIDGE_GATE_SYNC_HOURS` (default 6): people it served who are gone are revoked, at most `BRIDGE_RECONCILE_MAX_REVOKES` a round, and a round that would revoke everyone is never applied. A gate's `new_user.budget` gives each auto-provisioned person a token budget, which other replicas pick up within `LOOMCYCLE_LIMITS_RELOAD_INTERVAL` (default 1 min).
- **Not defended:** Telegram, Discord and Teams expose no member list, so a person removed there keeps access until the platform tells the bridge or an operator revokes them. With the in-memory store, kept revokes and reconciliation history are lost on restart. See [`packages/bridge-core/README.md`](packages/bridge-core/README.md#as-a-loomcycle-gate).

### Credentials, the Crypto tool and KMS

- **Tenant credentials** (CredentialDef) are sealed with AES-256-GCM under a per-tenant key derived (HKDF) from `LOOMCYCLE_SECRET_KEY`, the row's identity bound as additional data. Without the key nothing is stored or opened; a row that will not open is unusable and never falls back to the operator's key. `LOOMCYCLE_SECRET_KEY_PREVIOUS` opens rows sealed before a rotation, which are re-sealed on write. Credentials are not in snapshots.
- **`allowed_urls`** restricts where a credential may be sent: it is resolved only for a destination it covers, with no redirect followed. The `Git` tool refuses a credential without `allowed_urls`; the Crypto tool refuses a restricted credential as key material.
- **OAuth-connected credentials (`$oauth:<name>`)** hold a connection to an OAuth-protected MCP server. Their owner connects them outside a run by approving a device code (RFC 8628) in a browser; loomcycle then refreshes the access token itself, one refresh in flight per credential across replicas, storing the rotated refresh token before handing out the new access token. The access token, refresh token, device code and client registration are sealed like any credential and never reach the model, the owner or the operator; the access token is sent only to the credential's `allowed_urls` (the resource by default) with no redirect followed, and every discovered endpoint must be https on the issuer's or resource's host. An MCP server's `401 invalid_token` triggers one refresh and one retry of the refused request; a second refusal, or a refresh the server refuses, moves the credential to `needs_reauth`, and a credential that is not connected fails the call; nothing stands in for it. The display name `connected_as` comes from the userinfo endpoint or a verified `id_token` (asymmetric signature from the issuer's own JWKS, exact issuer and audience, unexpired), and the `id_token` itself is never stored. Snapshots carry the settings, never a token or the registration, and restore as `needs_reauth`. See [`docs/CREDENTIALS.md`](docs/CREDENTIALS.md#connecting-through-oauth--oauthname).
- **KMS.** Crypto-tool keys may live in Vault Transit, AWS KMS or Google Cloud KMS, where loomcycle stores a reference and the key never leaves the KMS. The master key `LOOMCYCLE_SECRET_KEY` itself is not KMS-wrapped: it comes from the environment, and it also derives the token pepper, the password pepper and the audit-chain HMAC key. Protect it like a root credential. The external credential-store backends (Vault, cloud secret managers, 1Password) are not implemented. See [`docs/CREDENTIALS.md`](docs/CREDENTIALS.md#enabling-it-operator).

### The loomcycle.cloud deployment

`cloud-deployment/` and `cloud-web/` describe one hosted instance, not a property of the runtime. Sign-up is gated by Cloudflare Access; a signed-up person is a **pending** member of one shared tenant until a tenant operator approves them. An approved person is a non-isolated member of that shared tenant: everything in [Tenant members](#tenant-members) applies, including that the tenant scope is shared with every other approved member. The sign-up website holds an `auth:manage` token (owner recovery off). That deployment does not yet require a second factor and still offers the paste-a-token sign-in beside the password gate; its compose file defaults `LOOMCYCLE_ACL` to `shadow`, where an explicit access-control deny is logged, not enforced (see [Access control](#access-control)). The documented residuals of that deployment (an `*` HTTP host allowlist, the builder sidecar's Docker socket) are in [`cloud-deployment/README.md`](cloud-deployment/README.md#security-posture-read-before-exposing-publicly).

### The Web UI bundle and response headers

- The Web UI is embedded in the binary. An operator may load a newer bundle at runtime from `LOOMCYCLE_WEBUI_DIR`, or from `LOOMCYCLE_WEBUI_BUNDLE_URL` (https, no user information) checked against `LOOMCYCLE_WEBUI_BUNDLE_SHA256`; a failed check falls back to the embedded UI. A loaded bundle runs with the signed-in operator's session, so it is as trusted as the binary, and Web UI bundles are not signed: pin the SHA-256 from a release you verified.
- Every response carries `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, and HSTS when `LOOMCYCLE_PUBLIC_URL` is https. A response that is not a page gets `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`; the Web UI's own policy admits only its origin and its inline scripts by hash; inbox downloads are sandboxed.

### Supply chain and releases

- Release archives carry an SPDX SBOM and a third-party license bundle; the checksum file is signed keyless with cosign; archives and container images carry GitHub build-provenance attestations, and images are cosign-signed. [`docs/VERIFYING-RELEASES.md`](docs/VERIFYING-RELEASES.md) shows how to check each, and [what it does not cover](docs/VERIFYING-RELEASES.md#what-is-not-covered).
- CI gates every pull request on `govulncheck`, gosec at medium severity and high confidence, `npm audit --omit=dev --audit-level=high` over every lockfile, and `pip-audit` for the Python adapter; CodeQL runs on Go and TypeScript. Every workflow action is pinned by commit SHA and every base image by digest, with dependabot moving them. Scanner dismissals are recorded in [`docs/SECURITY-TRIAGE.md`](docs/SECURITY-TRIAGE.md).
- npm packages publish through npm trusted publishing (the workflow's GitHub OIDC identity, no long-lived `NPM_TOKEN`) with SLSA provenance; the Python package publishes through PyPI's trusted publisher with attestations.
- `main` is protected by a repository ruleset (a GitHub setting, not a file in this tree): no deletion or force-push; every change through a squash-merged pull request with resolved review threads; 15 required checks — `CI ok` (which fails unless every CI job passed), `govulncheck` and gosec on each of the five Go modules, `npm audit`, `pip-audit` and CodeQL for Go and TypeScript; CodeQL must report no alert of high severity or above; nobody may bypass it.
- **Not yet:** the ruleset requires no approving review, and there is one maintainer ([`MAINTAINERS.md`](MAINTAINERS.md)).

### What is in scope, what is not

A way around one of these documented boundaries — a tenant reaching another tenant's data, a member reaching another member's user scope without a browse grant, a run exercising operator authority, a model widening an operator's allowlist, a Bashbox command escaping its volume, a database writer without the key editing the audit chain unnoticed — is in scope. So is anything that leaks a secret, a credential or a bearer token.

Out of scope: vulnerabilities in model providers, third-party MCP servers or other upstream services (report those to their owners), findings that need an operator to have disabled a documented protection, and the residuals this section lists as not defended.

The [security highlights](README.md#security-highlights) in the README summarize the default-deny model.
